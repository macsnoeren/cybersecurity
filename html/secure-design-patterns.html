01 · Architecture

Architecture-Level Security Patterns

These patterns shape the overall structure of a system — how components are divided, how trust boundaries are placed, and how security is layered in from the start. Getting these right early prevents whole classes of vulnerabilities. Changing them later is expensive or impossible.

StructuralHigh impactDesign phaseHard to retrofit
Patterns
🔪
Distrustful Decomposition
Privilege Separation · PrivSep

Split a system into separate processes or components with minimal trust between them. Each part operates with only the privileges it needs. If one component is compromised, the attacker cannot easily reach the others. Derived from OpenSSH's PrivSep model.

PrivSep PatternDiagram
Network
   ↓
[Unprivileged Child]  ← handles network I/O
   ↓ (validates, passes sanitized data)
[Privileged Parent]   ← minimal footprint
   ↓ (only acts on validated requests)
[Protected Resource]  ← DB, filesystem, keys

Attacker exploiting network child:
  → gains ZERO privileges on parent
Pattern Context
Problem:Monolithic processes expose all resources if any part is exploited
Solution:Split into unprivileged (untrusted input) + privileged (resource access) processes
Source:OpenSSH, BIND, Chrome (renderer/browser process split), Firefox
When to apply
System handles untrusted network input AND needs privileged resource access
Network-facing daemons (web servers, SSH, DNS, mail)
Browsers: renderer processes handle untrusted HTML; browser process holds OS resources
Any service where a network exploit should not grant system access
Anti-Pattern (avoid)
Running the entire web server as root or as a user with DB access
Single process that handles both untrusted user input and crypto key operations

Defense in Depth
Layered Security · Concentric Rings

Deploy multiple independent security layers so that a failure in any single control does not result in a system compromise. Each layer assumes the previous one may have already been breached. Like plywood sheets with random holes — two sheets prevent all light from getting through even if individual sheets have holes.

LayersWeb App Example
[ WAF / CDN         ]  ← blocks known attack patterns
[ Load Balancer     ]  ← rate limiting, DDoS
[ Authentication    ]  ← MFA, identity verification
[ Authorization     ]  ← RBAC, ABAC, policy checks
[ Input Validation  ]  ← all inputs validated server-side
[ Parameterized SQL ]  ← prevents injection
[ Encrypted Storage ]  ← AES-256 at rest
[ Audit Logging     ]  ← detect if all else fails
When to apply
Always — no single control is sufficient for any system handling sensitive data
Compliance environments requiring layered controls (PCI-DSS, ISO 27001)
High-value targets: financial systems, health data, identity providers
Benefits
Limits blast radius of any single failure
Attacker must defeat multiple independent controls
Tradeoffs
Adds complexity and operational overhead
Layers must be truly independent

Minimise Attack Surface
Economy of Mechanism · Keep it Simple

Every feature, API endpoint, open port, and code path is potential attack surface. Reduce what exists rather than trying to secure everything. Disable unused features, close unnecessary ports, remove unused code, and expose minimal interfaces. Simpler systems have fewer bugs.

Attack Surface ReductionChecklist
# Reduce exposed surface
✗ Admin panel exposed to internet
✓ Admin panel on internal network only

✗ DEBUG=True in production
✓ Debug endpoints disabled in prod

✗ All HTTP verbs accepted on all routes
✓ Only GET/POST allowed where needed

✗ 30 npm packages, 20 unused
✓ Minimal dependencies, audited
When to apply
During design: question every feature — "is this necessary?"
API design: expose only required endpoints with minimum HTTP methods
Server hardening: disable all services, open only what is needed
Dependency management: audit and remove unused packages regularly

Secure by Default
Fail-Safe Defaults · Deny by Default

Systems should ship with secure configuration out of the box. Every optional feature is disabled. Every permission is denied unless explicitly granted. Users should not need to manually enable security — insecure behavior should require explicit opt-in. Based on Saltzer & Schroeder's "fail-safe defaults."

Access Control DefaultPython
# BAD: allowlist with fallthrough to grant
def check_access(user, resource):
    if user.role == "admin":
        return True
    if user.owns(resource):
        return True
    return True  # ← Bug: grants everyone!

# GOOD: deny by default, grant explicitly
def check_access(user, resource):
    if user.role == "admin":
        return True
    if user.owns(resource):
        return True
    return False  # ← Deny all others
When to apply
All access control logic — deny by default, allow by exception
Product configuration — ship with strongest settings, let users relax them
API design — no endpoint should be public unless explicitly marked
CISA Secure by Design guidance mandates this for software vendors
Anti-Pattern (avoid)
Shipping with default passwords (admin/admin) — e.g., Mirai botnet exploited millions of IoT devices this way
Opt-in security features (MFA optional, encryption optional)
References
🏛️CISA — Secure by Design Guidance↗

Zero Trust Architecture
Never Trust, Always Verify · BeyondCorp

Eliminate implicit trust based on network location. Every request must be authenticated, authorized, and encrypted regardless of origin — even requests from inside the corporate network. Assumes breach has already occurred. Pioneered by Google's BeyondCorp project.

Zero Trust vs PerimeterComparison
Perimeter model (OLD):
  inside network → trusted
  outside network → untrusted
  ↓ Breach = attacker moves freely inside

Zero Trust (NEW):
  every request → verify identity
  every request → verify device posture
  every request → check authorization
  every connection → encrypted (mTLS)
  every action → logged and audited
  access → just-in-time, minimum scope
When to apply
Cloud-native and hybrid architectures (no well-defined perimeter)
Remote workforce — employees accessing resources from untrusted networks
Microservices: each service authenticates to every other (mTLS)
Post-breach environments — assume attackers may already be inside
References
🌐Google BeyondCorp — Zero Trust Model↗ 🏛️NIST SP 800-207 — Zero Trust Architecture↗
Real-World Examples
OpenSSHPrivSep — Distrustful Decomposition

OpenSSH split into an unprivileged child (handles network) and a privileged monitor (manages keys/auth). Exploiting the network-facing code yields no privilege escalation. This pattern was specifically designed after early SSH vulnerabilities.

ChromeRenderer / Browser Process Split

Chrome runs each tab in an unprivileged renderer process. The browser process holds OS resources. A sandbox escape from malicious JavaScript requires two separate exploits: renderer escape + browser sandbox bypass. Classic distrustful decomposition.

Mirai 2016Failure of Secure-by-Default

The Mirai botnet infected 600,000+ IoT devices using a list of 61 default username/password combinations. Every single one shipped with default credentials. This DDoS'd Dyn DNS and took down Twitter, Reddit, and GitHub for hours.

Target 2013No Network Segmentation

Attackers entered through an HVAC vendor's credentials. Because the network wasn't segmented, they moved laterally to POS systems and stole 40M credit card numbers. A zero trust architecture would have prevented lateral movement.

02 · Access Control

Access Control Patterns

Ensure that only authorized subjects can perform authorized operations on authorized objects. These patterns implement the core security properties: authentication (who are you?), authorization (what can you do?), and complete mediation (check every access, every time). Poor access control is the #1 vulnerability class according to OWASP.

AuthenticationAuthorizationOWASP A01:2021Complete Mediation
Patterns
🛡️
Reference Monitor
Protection Proxy · Policy Enforcement Point

A single, tamper-proof access control component that mediates ALL access to protected resources. Every request goes through it — there are no shortcuts. It must be: always invoked (complete mediation), tamper-proof, and verifiable (small and simple enough to audit). The theoretical foundation of all access control.

Reference MonitorPython
# All resource access through one path
class ReferenceMonitor:
    def access(self, subject, action, resource):
        # 1. Authenticate subject (who are they?)
        if not self.authenticate(subject):
            raise AuthError()
        # 2. Authorize (are they allowed?)
        if not self.authorize(subject, action, resource):
            raise PermissionError()
        # 3. Log the access
        self.audit_log(subject, action, resource)
        # 4. Perform the operation
        return resource.execute(action)
Key properties
Always invoked:No bypass paths — every access goes through the monitor
Tamper-proof:The monitor itself cannot be modified by untrusted code
Verifiable:Small and simple enough to formally verify correctness
When to apply
Any system with protected resources and multiple access paths
API gateways centralizing auth/authz for downstream services
OS kernels: all syscalls go through kernel-level access checks
Anti-Pattern (avoid)
Scattering access checks throughout the codebase — easy to miss one
Checking auth at the UI layer only (API endpoints remain exposed)
References

👥
Role-Based Access Control (RBAC)
Also: ABAC · PBAC · ReBAC

Assign permissions to roles, not directly to users. Users are assigned roles. This decouples permission management from user management — changing a job function means changing a role assignment, not updating every permission. Scales well for large organizations.

RBAC ModelDiagram + Python
Users → Roles → Permissions → Resources
──────────────────────────────────────
alice → [editor, viewer] → read, write → /docs
bob   → [viewer]         → read        → /docs
carol → [admin]          → *           → /*

# Enforce: check role, not user identity
def can(user, action, resource):
    roles = get_roles(user)
    return any(policy.allows(r, action, resource)
               for r in roles)
When to apply
Multi-user systems with defined job functions (SaaS, enterprise apps)
Regulatory compliance (SOD — Separation of Duties) requirements
Use ABAC (attribute-based) when roles alone can't express fine-grained policies
Use ReBAC (relationship-based) for social/collaborative apps (e.g., Google Drive)

Complete Mediation
Always Re-check · No Cached Permissions

Every access to every resource must be checked at the time of use, not just at login time. Permissions can change. Sessions can be revoked. Never rely on a permission check performed earlier. TOCTOU vulnerabilities arise from violating this principle.

ATM ExamplePseudocode
# WRONG: check once, then trust indefinitely
balance = db.get(user)  # check at T1
# ... attacker withdraws on another ATM ...
if balance >= amount:   # stale data!
    dispense(amount)    # overdraft!

# CORRECT: atomic check-and-act
rows = db.execute(
    "UPDATE accounts SET balance = balance - ?"
    " WHERE id = ? AND balance >= ?",
    amount, user_id, amount)
if rows == 0:
    deny("Insufficient funds")
When to apply
Financial transactions — always recheck balance atomically
Session management — recheck permissions on sensitive operations, not just login
File access — use fstat() on open file descriptor, not stat() on path
Token revocation — support token introspection, don't rely on JWT expiry alone
References
📘OWASP Session Management Cheat Sheet↗
🔑
Least Privilege
Minimal Authority · Need-to-Know

Every user, process, and service operates with the minimum permissions needed to do its job — and nothing more. Limits blast radius: a compromised low-privilege account can only damage what it had access to. Applies to users, service accounts, OS processes, and database connections equally.

Service Account ScopingSQL + Python
-- WRONG: app uses DB superuser
GRANT ALL PRIVILEGES ON *.* TO 'app'@'%';

-- RIGHT: only what the app needs
GRANT SELECT, INSERT, UPDATE ON myapp.*
  TO 'app_user'@'app_host';
-- Separate read-only user for reports
GRANT SELECT ON myapp.reports
  TO 'report_user'@'report_host';

# Just-in-time elevation (AWS)
sts.assume_role(RoleArn=admin_role,
    DurationSeconds=900)  # 15 min only
When to apply
All service accounts and database credentials
IAM roles in cloud — scope to minimum required actions and resources
Linux processes — drop root after init, run as dedicated low-priv user
Just-in-Time (JIT) access — elevate privileges only for the duration of the task
Anti-Pattern (avoid)
Web app DB user with DROP TABLE or DBA privileges
CI/CD pipeline with production admin credentials permanently stored
References
🎓UC Berkeley CS 161 — Least Privilege Explained↗
🚧
Checkpoint / Chokepoint
Single Entry Point · Security Gateway

Force all traffic through a single controlled gateway where security controls are applied. Eliminates hidden access paths. Applies to network traffic (firewall, API gateway) and application logic (single auth middleware on all routes). One place to enforce, audit, and update policy.

API Gateway PatternNode.js / Express
// Apply auth middleware globally — no bypass
const app = express();

// Checkpoint: runs BEFORE all route handlers
app.use(authenticateRequest);  // verify JWT
app.use(authorizeRequest);   // check RBAC
app.use(rateLimiter);        // throttle
app.use(auditLogger);        // log all access

// Routes only run after all checks pass
app.get('/api/data', handler);
When to apply
API design — apply auth/authz middleware globally, not per route
Network architecture — all external traffic through WAF/firewall
Microservices — API gateway or service mesh handles all inter-service auth

03 · Input

Input & Validation Patterns

The root cause of injection attacks (SQLi, XSS, command injection, path traversal) is conflating untrusted data with trusted instructions. These patterns establish where, how, and in what form untrusted input is accepted, validated, and transformed before it reaches any structured output or sensitive system. Input validation is not a single check — it is a design concern.

Injection PreventionOWASP A03:2021AllowlistingCanonicalization
Patterns
🧪
Input Validation Pattern
Allowlist Validation · Canonicalize First

Validate all inputs from all sources before processing. Use allowlists (define what is valid) rather than blocklists (define what is invalid). Canonicalize before validating — normalize encoding so that "<script>" and "%3Cscript%3E" are both caught.

5-Stage ValidationProcess
Stage 1: Identify  all input sources
           URL, form, headers, cookies,
           files, env vars, DB, APIs

Stage 2: Canonicalize  normalize encoding
           URL-decode → strip BOM → to Unicode NFC

Stage 3: Allowlist  validate expected format
           regex, type check, range, length

Stage 4: Sanitize  remove/escape remaining risk
           HTML-encode output, parameterize SQL

Stage 5: Reject    on validation failure
           return error, never silently fix
When to apply
Every API endpoint, form field, and file upload
Validate on the server, not just in the browser (client-side can be bypassed)
Validate at every trust boundary, not just the outermost edge
Allowlist: only accept known-good patterns (not blocklist known-bad)
Anti-Pattern (avoid)
Validating before URL-decode (bypass: %27 for SQL quote)
Blocklisting specific dangerous characters — attackers find alternate encodings
References
📘OWASP Input Validation Cheat Sheet↗
🔗
Intercepting Filter
Middleware Chain · Filter Chain · Decorator

Apply a chain of independent security filters to every request before it reaches the application logic. Each filter handles one concern: authentication, input validation, rate limiting, logging. Filters are composable and can be added/removed without changing business logic.

Filter ChainPython / FastAPI
# Each middleware = one security filter
from fastapi import FastAPI
app = FastAPI()

# Filter 1: Rate limiting
app.add_middleware(SlowAPIMiddleware)
# Filter 2: Authentication
app.add_middleware(JWTAuthMiddleware)
# Filter 3: Input sanitization
app.add_middleware(InputSanitizeMiddleware)
# Filter 4: Security headers
app.add_middleware(SecurityHeadersMiddleware)

# Business logic never sees raw, unchecked input
When to apply
Web frameworks — apply security middleware globally to all routes
Separating cross-cutting security concerns from business logic
Adding security incrementally to existing systems without modifying every handler

☕Jakarta Servlet Filter (Java EE)↗
🗄️
Parameterize Everything
Prepared Statements · Structural Separation

Never construct structured output (SQL, HTML, shell commands, XML) by string concatenation with user input. Always use structural separation: the structure is defined in code, the data is passed separately. Parameterized queries are the canonical example — they completely prevent SQL injection.

SQL / Shell / HTMLPython
# SQL — parameterized query
query = "SELECT * FROM u WHERE name='"+n+"'"
cursor.execute("SELECT * FROM u WHERE name=?", [n])

# Shell — use list, not string
os.system("ping " + host)
subprocess.run(["ping", host], shell=False)

# HTML — encode output
f"<div>{user_name}</div>"
f"<div>{html.escape(user_name)}</div>"

# Template — pass as variable, not template code
Template(user_input).render()
Template("Hello {{name}}").render(name=user_input)
When to apply
Every database query — parameterized queries, not string concatenation
Every HTML output — context-sensitive encoding (HTML, JS, CSS, URL)
Every shell command — subprocess list args, shell=False
Every template — pass user data as variables, never as template code
References
📘OWASP SQL Injection Prevention↗ 📘OWASP XSS Prevention Cheat Sheet↗
✅
Allowlist over Blocklist
Positive Security Model · Whitelist

Define what is permitted rather than what is forbidden. Blocklists are inherently incomplete — attackers find new encodings, bypass characters, or edge cases you didn't think of. Allowlists fail closed (reject anything not explicitly permitted) rather than open (allow anything not explicitly blocked).

File Upload ValidationPython
# BLOCKLIST (WRONG) — easy to bypass
BLOCKED = ['.php', '.exe', '.js', '.sh']
if not any(name.endswith(b) for b in BLOCKED):
    save(file)  # .phtml? .php5? Missed!

# ALLOWLIST (RIGHT) — fails closed
ALLOWED_TYPES = {'image/jpeg', 'image/png', 'image/gif'}
ALLOWED_EXTS  = {'.jpg', '.jpeg', '.png', '.gif'}

ext = Path(filename).suffix.lower()
mime = magic.from_buffer(file.read(2048), mime=True)

if ext not in ALLOWED_EXTS or mime not in ALLOWED_TYPES:
    raise ValidationError("File type not permitted")
When to apply
File uploads — allowlist MIME types and extensions, verify magic bytes
Input fields — allowlist character sets per field (e.g., digits only for phone)
URL redirects — allowlist allowed destination domains
HTML sanitization — allowlist tags/attributes (DOMPurify, bleach)

04 · Data Protection

Data Protection Patterns

Ensure that sensitive data is protected at rest, in transit, and during processing. These patterns govern how data is hidden, encrypted, and communicated — and crucially, what information should never be exposed to attackers through error messages, API responses, or side channels.

ConfidentialityIntegrityData MinimizationInformation Hiding
Patterns
🔐
Secure Channel
Encrypted Transport · TLS Everywhere

All communication between components must use authenticated, encrypted channels. Not just external-facing HTTPS — also service-to-service, service-to-database, and internal API calls. Encryption without authentication is insufficient (MITM attacks).

mTLS Service-to-ServiceGolang
// Both sides verify each other's identity
tlsConfig := &tls.Config{
    // Server verifies client cert
    ClientAuth: tls.RequireAndVerifyClientCert,
    ClientCAs:  clientCACertPool,
    // Client verifies server cert
    RootCAs:    serverCACertPool,
    // Minimum TLS 1.3
    MinVersion: tls.VersionTLS13,
    // Explicitly restrict cipher suites
    CipherSuites: []uint16{
        tls.TLS_AES_256_GCM_SHA384,
    },
}
When to apply
All external-facing services — HTTPS (TLS 1.3 minimum)
Microservices — mutual TLS (mTLS) for service-to-service auth
Database connections — TLS even on internal network
Queue/message brokers — TLS + auth on Kafka, RabbitMQ, etc.
References
📘OWASP TLS Cheat Sheet↗ 🕸️Istio — mTLS in Service Mesh↗
🛡️
Exception Shielding
Error Abstraction · Safe Error Messages

Never expose internal implementation details through error messages. Stack traces, SQL errors, file paths, and class names give attackers a map of your system. Return generic, safe error messages to clients; log full details internally only.

Error HandlingPython
# WRONG: leaks DB structure to client
except Exception as e:
    return {"error": str(e)}
# → "column 'password' of relation 'users'..."

# RIGHT: shield internals, log privately
except Exception as e:
    error_id = generate_uuid()
    logger.error(f"[{error_id}] {traceback.format_exc()}")
    return {"error": "An internal error occurred",
            "id": error_id}  # user can report this ID
When to apply
All API endpoints — catch all exceptions at the outermost layer
Authentication failures — return generic "Invalid credentials" (not "user not found")
Production environments — disable framework debug modes
Error correlation — include a reference ID so internal logs can be matched to user reports
Anti-Pattern (avoid)
Django DEBUG=True in production — exposes stack trace, settings, SQL queries
Different error messages for "user not found" vs "wrong password" — enables user enumeration
References
📘OWASP Error Handling Cheat Sheet↗

Data Minimization
Limited View · Need-to-Know Data · Privacy by Design

Collect, retain, and expose only the minimum data necessary. Data you don't have can't be stolen. Reduce both what you store and what you return in API responses. Return only fields the requester is authorized to see.

Limited View / Field FilteringPython
# WRONG: return entire user object
return db.get_user(user_id)  
# → {id, name, email, password_hash, 
#    ssn, credit_card, internal_notes}

# RIGHT: return only what is needed for context
def get_public_profile(user_id):
    user = db.get_user(user_id)
    return {
        "id":    user.id,
        "name":  user.display_name,
        "avatar": user.avatar_url
        # password_hash, SSN: never exposed
    }
When to apply
API design — define response schemas that exclude sensitive fields
GDPR/CCPA compliance — collect only what you have a legal basis for
Logging — never log passwords, tokens, credit cards, or SSNs
Database design — use separate tables for sensitive vs non-sensitive data

Secure Logger / Audit Trail
Tamper-Evident Log · Audit Interceptor

Security-relevant events must be logged in a tamper-evident, append-only store. Logs are the primary mechanism for detecting breaches and for forensic analysis. They must be protected from modification by the same attacker you are trying to detect.

What to logChecklist
✓ Authentication: login success/failure + IP
✓ Authorization: access denied events
✓ Privilege changes: role granted/revoked
✓ Data access: who read/modified sensitive data
✓ Config changes: security settings modified
✓ Errors: validation failures, exceptions

✗ Passwords, tokens, credit card numbers
✗ PII beyond minimum identification

Each log entry: timestamp, user, IP,
action, resource, outcome, correlation_id
When to apply
All security events — auth, authz, data access, config changes
Ship logs to a separate, write-only store attackers cannot reach
Compliance requirements (PCI-DSS, SOC2, ISO 27001 all mandate audit trails)
Incident response — logs are the only reliable evidence after a breach

05 · Error & State

Error & State Patterns

Systems always fail eventually — the question is how they fail. These patterns ensure that failures move the system to a known, safe state rather than an inconsistent or open state. They also address how security logic gates user-accessible functionality through explicit state machines.

Fail SecureResilienceState ConsistencyAvailability
Patterns
🔒
Fail Secure (Fail Closed)
Safe Failure · Secure Default on Error

When a security component fails, it should deny access rather than grant it. A firewall that crashes should drop all traffic. An auth service that errors should reject the request. The opposite — "fail open" — is a common and catastrophic mistake.

Authorization HandlerPython
# FAIL OPEN (WRONG)
def authorize(token, resource):
    try:
        return check_permission(token, resource)
    except Exception:
        return True  # ← grants access on error!

# FAIL CLOSED (RIGHT)
def authorize(token, resource):
    try:
        return check_permission(token, resource)
    except AuthServiceDown:
        log.error("Auth service unavailable")
        return False  # ← deny on error
    except InvalidToken:
        return False
    except Exception:
        log.exception("Unexpected auth error")
        return False  # ← always deny on uncertainty
When to apply
Authorization services — any exception → deny access
Network controls — firewall default policy: DROP (not ACCEPT)
Circuit breakers — fail closed when downstream auth service is unavailable
HMAC/signature verification — exception = reject, never accept
Anti-Pattern (avoid)
Catch-all exception handler that returns True or grants access
Firewall default policy: ACCEPT (should be DROP with explicit ALLOW rules)
References
📘Cydrill — Secure Design Principles Deep Dive↗

Secure State Machine
Security State Control · Gated Transitions

Separate security state (authentication, authorization level) from functional state (what the user can do). Functional operations are only available after the security state machine has transitioned to the correct state. Users cannot skip the authentication step to reach protected functionality.

Login FlowState Diagram
[UNAUTHENTICATED]
      ↓ submit credentials
  (validate password)
      ↓ success
[PASSWORD_VERIFIED]
      ↓ OTP sent
  (validate OTP code)
      ↓ success
[AUTHENTICATED]
      ↓ access granted to protected resources
      
Security state machine controls which
functional states are accessible.
Cannot jump directly to [AUTHENTICATED].
When to apply
Multi-step authentication flows (password + MFA)
Checkout flows — ensure payment is verified before confirming order
Any workflow where steps must occur in order for security
Preventing state skip attacks — jumping to step 3 without completing steps 1 and 2
References
🎓SEI CMU — Secure State Machine Pattern↗
💾
Checkpointed System
Rollback · Known-Good State Recovery

Periodically save system state to a known-good checkpoint. If a failure or compromise is detected, the system can roll back to the last verified-safe state. Critical for high-availability systems that must recover from partial failures without human intervention.

Recovery PatternPseudocode
Recovery Proxy  ←→  Recoverable Component
                           ↓
                    takes periodic snapshots
                           ↓
          on failure detected by proxy:
          1. stop operations
          2. restore from last checkpoint
          3. replay verified transactions
          4. resume normal operations

Examples:
  Database WAL + point-in-time recovery
  VM snapshots
  Immutable infrastructure (redeploy)
When to apply
Databases — WAL (Write-Ahead Log) for transactional consistency
Ransomware resilience — immutable backups to a separate, isolated location
Infrastructure — immutable server images (redeploy rather than patch in place)
Incident response — ability to roll back to a known-clean state

Rate Limiting & Circuit Breaker
Throttling · Bulkhead Pattern

Limit the rate of requests and automatically cut off failing components. Prevents brute force, credential stuffing, and DoS. Circuit breakers prevent cascading failures — when a dependency fails, requests fail fast instead of queuing up and exhausting resources.

Rate Limit + Circuit BreakerPython
# Rate limiting — login endpoint
@rate_limit(max=5, window="15min", by="ip+user")
def login(username, password):
    ...

# Circuit breaker state machine
CLOSED  → calls pass through normally
    ↓ failures exceed threshold
OPEN    → all calls fail immediately (fast fail)
    ↓ after timeout (e.g., 60s)
HALF-OPEN → allow one probe call
    ↓ probe success → back to CLOSED
    ↓ probe failure → back to OPEN
When to apply
Authentication endpoints — prevent brute force and credential stuffing
Password reset / OTP — rate limit to prevent enumeration
Service-to-service calls — circuit breaker prevents cascading failures
APIs — per-user and per-IP rate limiting to prevent abuse
References
🌐Microsoft — Circuit Breaker Pattern↗ 📘OWASP Authentication Cheat Sheet (rate limiting)↗
2003 Northeast BlackoutFail Open — Cascading Failure

A software bug caused a monitoring system to fail silently (fail open). Operators didn't know lines were overloaded. No circuit breaker. A local failure cascaded across 8 states and 55M people lost power. Secure state management could have isolated the failure.

Rockstar Games 2022State Skip Attack

GTA Online's anticheat could be bypassed by sending a specifically crafted message that skipped authentication state checks. The secure state machine pattern — requiring explicit state transitions — would have prevented this attack vector.

Colonial Pipeline 2021No MFA = State Machine Failure

A single compromised VPN password was sufficient to gain access because MFA was not required. A secure state machine would have required a second factor transition before granting network access — the attack would have stopped at step 1.

06 · Implementation

Implementation-Level Secure Design Patterns

These patterns from the SEI CMU Secure Design Patterns catalog (2009) describe how to implement concrete security-aware code structures. They extend classical GoF patterns (Factory, Strategy, Visitor, State) with security constraints — selecting behavior based on trust level, preventing unauthorized access to data structures, and encoding trust level into object creation.

Secure Factory
Trust-Aware Object Creation · Controlled Object Factory

Create objects that are appropriately scoped for the trust level of the requester. The factory inspects security credentials and returns a trust-level-appropriate object. Untrusted callers get a restricted object; trusted callers get a full-capability object. Prevents accidentally giving high-privilege objects to untrusted code.

Secure FactoryPython
class UserContextFactory:
    def create(self, credentials) -> UserContext:
        trust = self.evaluate_trust(credentials)

        if trust == TrustLevel.ADMIN:
            return AdminUserContext(credentials)
        elif trust == TrustLevel.USER:
            return StandardUserContext(credentials)
        elif trust == TrustLevel.GUEST:
            return ReadOnlyContext(credentials)
        else:
            return UntrustedContext()
            # Untrusted: minimal info, no ops
When to apply
Multi-tier APIs where different callers get different capabilities
Error message generation — untrusted clients get generic errors; trusted clients get details
Configuration objects — admin gets write access, regular user gets read-only view

Strategy Factory
Trust-Aware Strategy Selection

Select a different strategy (algorithm/behavior) based on the trust level of the caller. The same operation performs differently depending on who is calling. Separates trust-level selection logic from business logic — tested independently.

XML-RPC Error ResponsePython
# Different error detail per trust level
class ErrorResponseFactory:
    strategies = {
        TrustLevel.INTERNAL: DetailedErrorStrategy,
        TrustLevel.PARTNER:  PartnerErrorStrategy,
        TrustLevel.PUBLIC:   GenericErrorStrategy,
    }
    def get_strategy(self, credentials):
        trust = evaluate_trust(credentials)
        cls = self.strategies.get(trust,
              GenericErrorStrategy)
        return cls()

# Internal caller: full stack trace + context
# Partner:         error code + category
# Public:          "An error occurred"
When to apply
Error handling — internal tools get full details, external clients get generic messages
Data serialization — admin gets all fields, public API gets redacted view
Logging verbosity — internal trusted callers get verbose logs; external don't

Secure Visitor
Credential-Gated Traversal

When traversing a hierarchical data structure, nodes unlock themselves only to visitors that present valid credentials. The node checks whether the visitor is authorized to see its data and returns only an unlocked (data-accessible) version if authorized — or nothing if not. Prevents accessing parent/sibling data through an unlocked child.

Locked Node TraversalPython
class DataNode:  # locked by default
    def accept(self, visitor):
        # Check before unlocking
        if visitor.credentials.can_access(self.id):
            unlocked = UnlockedDataNode(self.data)
            # Unlocked has NO reference to parent!
            visitor.visit(unlocked)
        # else: silently skip (no info leak)

class UnlockedDataNode:
    def __init__(self, data):
        self.data = data
        # No parent, no siblings, no children refs
When to apply
File system traversal — user can only see files they are authorized for
Document hierarchies — a user authorized for a child node should not see the parent
Graph-based authorization — social network data, org charts with sensitivity levels

Defer to Kernel / Trusted Computing Base
TCB · OS Security Delegation

Use OS-provided security mechanisms rather than reimplementing them. The kernel's security subsystem is well-tested, formally verified in some cases, and much harder to subvert than application-level implementations. Reinventing authentication, crypto, or access control at the application layer is almost always worse.

Use OS PrimitivesExamples
# File permissions — use OS ACLs
app.check_user_owns_file(path)  # own impl
os.access(path, os.R_OK)        # kernel ACL

# Crypto — use OS entropy
random.seed(time.time())        # predictable!
secrets.token_bytes(32)          # OS CSPRNG

# Secret storage — use OS keychain
config = {"api_key": "hardcoded"}
keyring.get_password("app","api_key")
When to apply
Key generation — always use OS CSPRNG (secrets, urandom)
File access control — defer to OS filesystem permissions
Secret storage — use OS keychain/credential store, not config files
Cryptography — use vetted libraries (OpenSSL, libsodium), never roll your own
Anti-Pattern (avoid)
Implementing your own hash function, RNG, or cipher
Reimplementing access control when the OS already provides it

Open Design
Kerckhoffs' Principle · No Security by Obscurity

Security must not depend on the secrecy of the design or algorithm. Assume attackers know every detail of your implementation. The only secret should be the key (or password). Systems that rely on "attackers won't know about this endpoint" are easily broken once discovered.

Kerckhoffs' PrincipleConcept
Security through obscurity (WRONG):
  "attackers won't know our API path"
  "our encryption algorithm is secret"
  "we renamed /admin to /mgmt-9x3k"

Open design (RIGHT):
  Publish the algorithm — keep only the key secret
  Use AES-256 (public) + secret key (private)
  Assume attacker finds the "hidden" URL
  → require authentication regardless

Kerckhoffs (1883): "A cryptosystem should
be secure even if everything about it,
except the key, is public knowledge."
When to apply
Cryptography — always use published, audited algorithms, not proprietary ones
API security — secure endpoints regardless of whether their path is "known"
Configuration — assume attackers can read your config files; secrets must be separate
Source code — assume breach; don't embed secrets in code ("it's private repo")
References

Psychological Acceptability
Usable Security · Human Factors

Security mechanisms that are too burdensome will be circumvented by users. If MFA is too hard, users will share accounts. If passwords requirements are too complex, users write them on sticky notes. Security and usability must be designed together — friction should be proportional to risk.

Usable Security DesignGuidelines
BAD: Security friction that causes workarounds
  Password must be 24+ chars, changed monthly
  MFA required for every page load
  CAPTCHA on every form interaction

GOOD: Risk-proportionate security UX
  Password manager support (long passphrases)
  MFA required only for login + sensitive ops
  Passwordless (passkeys) — more secure AND easier
  SSO — one strong login, not many weak ones
  Step-up authentication on sensitive actions
When to apply
Authentication UX — adopt passkeys and password managers; reduce forced rotation
Security dialogs — clear, specific, actionable messages (not "Are you sure?")
Onboarding — guide users toward secure defaults without overwhelming them
Developer tools — security controls that are easy to use correctly are used correctly
