Software VulnerabilitiesSoftware Kwetsbaarheden

Four general categories of software vulnerabilities — each with many real-world manifestations. Understanding these is the foundation of writing secure software.

Vier algemene categorieën van softwarekwetsbaarheden — elk met vele praktijkvoorbeelden. Het begrijpen hiervan is de basis voor het schrijven van veilige software.

⚠️
Complexity warning: Only four general categories does not mean this is easy. Each category contains dozens of real-world vulnerability types, and exploiting or preventing them requires deep expertise. This reference is a starting point — not a complete guide. Complexiteitswaarschuwing: Slechts vier categorieën betekent niet dat het eenvoudig is. Elke categorie bevat tientallen soorten kwetsbaarheden, en het misbruiken of voorkomen ervan vereist diepgaande expertise. Dit is een startpunt — geen volledige gids.
Category 01 · Memory Safety

Memory Management VulnerabilitiesGeheugenbeheer Kwetsbaarheden

Memory stores variables, executable code, and function return addresses. When an attacker can read or write outside intended memory boundaries, they can modify control flow, leak sensitive data, or execute arbitrary code — potentially gaining full system access.

Geheugen slaat variabelen, uitvoerbare code en functie-retouradressen op. Wanneer een aanvaller buiten de bedoelde geheugengrenzen kan lezen of schrijven, kunnen ze de control flow wijzigen, gevoelige data lekken of willekeurige code uitvoeren — wat kan leiden tot volledige systeemovername.

Code executionCode-uitvoering Privilege escalationRechtenescalatie Data exfiltrationData-exfiltratie System compromiseSysteemcompromis Critical severityKritieke ernst
Vulnerability Types

Buffer Overflow
CWE-120 / CWE-121 (Stack) / CWE-122 (Heap)

Writing more data into a buffer than it can hold, overwriting adjacent memory. Stack overflows can overwrite return addresses to redirect execution; heap overflows corrupt heap metadata or adjacent objects.

Meer data in een buffer schrijven dan deze kan bevatten, waardoor aangrenzend geheugen wordt overschreven. Stack overflows kunnen retouradressen overschrijven om de uitvoering om te leiden; heap overflows corrumperen heap-metadata of aangrenzende objecten.

● vulnerableC
// No bounds check — attacker controls input
void copy_input(char *input) {
    char buf[64];
    strcpy(buf, input); // DANGEROUS
}

// Safe alternative
void copy_input_safe(char *input) {
    char buf[64];
    strncpy(buf, input, sizeof(buf) - 1);
    buf[sizeof(buf)-1] = '\0';
}
How it worksHoe het werkt
1.Attacker sends input larger than the buffer sizeAanvaller stuurt input groter dan de buffergrootte
2.Excess bytes overwrite adjacent stack/heap memoryOvertollige bytes overschrijven aangrenzend stack/heap geheugen
3.Return address or function pointer is overwrittenRetouradres of functiepointer wordt overschreven
4.CPU jumps to attacker-controlled code (shellcode)CPU springt naar code van de aanvaller (shellcode)
MitigationsMitigaties
Use safe string functions (strncpy, strlcpy, snprintf)Gebruik veilige stringfuncties (strncpy, strlcpy, snprintf)
Enable stack canaries (compiler flag -fstack-protector)Schakel stack canaries in (compiler flag -fstack-protector)
Enable ASLR (Address Space Layout Randomization)Schakel ASLR in (Address Space Layout Randomization)
Enable DEP/NX (non-executable stack/heap)Schakel DEP/NX in (niet-uitvoerbare stack/heap)
Use memory-safe languages (Rust, Go) where possibleGebruik geheugenveilige talen (Rust, Go) waar mogelijk
Learn more

Use-After-Free (UAF)
CWE-416

Accessing heap memory after it has been freed. The freed chunk can be reallocated to another object; the original pointer now points into attacker-controlled data, enabling type confusion or code execution.

● vulnerableC
char *ptr = malloc(100);
free(ptr);
// ... attacker allocates here ...
strcpy(ptr, "data"); // UAF!

// Safe: nullify after free
free(ptr);
ptr = NULL; // Prevents accidental reuse
How it works
1.Object A is allocated and a pointer is kept
2.Object A is freed but pointer not nullified
3.Attacker allocates Object B at the same address
4.Old pointer now references attacker-controlled Object B
Mitigations
Set pointers to NULL immediately after free()
Use smart pointers in C++ (unique_ptr, shared_ptr)
Employ memory-safe languages (Rust's borrow checker)
Use AddressSanitizer (ASan) during testing
Learn more

Integer Overflow / Underflow
CWE-190 / CWE-191

Arithmetic results exceed the maximum (or minimum) value of the integer type, wrapping around to an unexpected value. Commonly leads to undersized buffer allocations or bypassed length checks.

● vulnerableC
size_t len = attacker_controlled_len;
// If len = SIZE_MAX, len+1 wraps to 0!
char *buf = malloc(len + 1);
memcpy(buf, src, len); // heap overflow

// Safe: check before arithmetic
if (len >= SIZE_MAX) return ERROR;
char *buf = malloc(len + 1);
Mitigations
Always validate integer bounds before arithmetic on untrusted values
Use safe integer libraries (SafeInt, checked_add in Rust)
Enable compiler warnings (-Winteger-overflow)
Use static analysis tools that detect integer issues
Learn more

Null Pointer Dereference
CWE-476

Dereferencing a NULL pointer causes undefined behavior. In userspace this usually crashes the program (DoS). In kernel code it can be exploited for privilege escalation via NULL pointer dereference techniques.

● vulnerableC
User *u = find_user(id);
// u may be NULL if user not found!
printf("%s", u->name); // CRASH

// Safe: always null-check first
if (u == NULL) { return NOT_FOUND; }
printf("%s", u->name);
Mitigations
Always check return values of functions that may return NULL
Use optional types (Rust Option, C++ std::optional)
Enable static analysis tools to detect null dereferences

Format String Attack
CWE-134

When user input is used directly as a printf format string, the attacker controls format specifiers (%x, %n). This can leak stack contents (%x) or write to arbitrary memory addresses (%n).

● vulnerableC
// User controls 'input'
printf(input);  // DANGEROUS!
// Input "%x %x %x" leaks stack
// Input "%n" writes to memory

// Safe: always use a literal format
printf("%s", input);
Mitigations
Never pass user-controlled data as printf format string
Always use a literal format string: printf("%s", user_input)
Enable compiler warnings (-Wformat-security)

Heap Spray
CWE-119

An exploitation technique — not a standalone bug — where the attacker fills large amounts of heap memory with shellcode/NOP sleds. Combined with another memory vulnerability, it increases the probability of jumping to attacker-controlled code.

Mitigations
ASLR makes spray targets unpredictable
Heap randomization and guard pages
Control-Flow Integrity (CFI) prevents arbitrary jumps
Limit large allocation patterns in untrusted context

Double Free
CWE-415

Calling free() twice on the same pointer corrupts heap metadata, which allocators use internally. This can be abused to redirect subsequent allocations or execute arbitrary code.

● vulnerableC
char *p = malloc(64);
free(p);
// ... error path also calls free ...
free(p); // heap corruption!

// Safe
free(p); p = NULL;
if (p) { free(p); } // no-op
Mitigations
Set pointer to NULL after every free()
Use smart pointers or RAII patterns in C++
Static analysis tools detect double-free paths

Out-of-Bounds Read
CWE-125

Reading beyond the allocated bounds of a buffer exposes adjacent memory contents — potentially revealing passwords, keys, or other sensitive data. The famous Heartbleed bug was an out-of-bounds read in OpenSSL.

● Heartbleed patternC
// Client sends: payload_length=64KB
// Actual data:  payload_length=3 bytes
memcpy(response, payload,
       attacker_claimed_length); // reads past buffer
// Returns up to 64KB of heap memory!
Mitigations
Always validate claimed lengths against actual buffer size
Use bounds-checked abstractions (std::span in C++)
Enable ASan / Valgrind in testing pipelines

Real-World Incidents
2014 Heartbleed (CVE-2014-0160) OOB Read

Out-of-bounds read in OpenSSL's TLS heartbeat extension. Allowed reading up to 64KB of server memory per request — exposing private keys, passwords, and session tokens without leaving a trace.

Impact: ~500,000 servers vulnerable; forced mass certificate revocations worldwide.

2017 WannaCry (EternalBlue) Buffer Overflow

NSA-developed exploit targeting a buffer overflow in Windows SMBv1. Used as the propagation mechanism for the WannaCry ransomware outbreak that spread to 150+ countries.

Impact: $4–8 billion in damages; NHS hospitals, FedEx, and Telefónica disrupted.

2021 Log4Shell (CVE-2021-44228) Memory / RCE

Remote code execution via JNDI injection in Apache Log4j. Attackers could trigger arbitrary class loading simply by getting their string logged by a vulnerable application.

Impact: CVSS 10.0; hundreds of millions of systems affected.

2022 Follina (CVE-2022-30190) Use-After-Free

Use-After-Free in Microsoft Support Diagnostic Tool (MSDT) triggered via malicious Office documents. No macros required — simply previewing the document was enough.

Impact: Zero-day exploited in the wild before patch was available.

Category 02 · Injection

Structured Output Vulnerabilities

When user-controlled data is embedded in a structured output (SQL query, HTML page, shell command, file path) without proper encoding, attackers can break the structure and inject their own commands or markup. The root cause is always the same: conflating data and instructions.

Data theft Authentication bypass Remote code execution Full system access Critical severity
Vulnerability Types
🗄️
SQL Injection
CWE-89 · OWASP A03:2021

User input is concatenated directly into SQL queries. Attackers can break out of the string context to add their own SQL — bypassing authentication, extracting entire databases, or deleting data.

● vulnerablePython
# Input: ' OR '1'='1
query = "SELECT * FROM users WHERE "
        "name='" + user_input + "'"
# Becomes: WHERE name='' OR '1'='1'
# Returns ALL users!

# Safe: parameterized query
query = "SELECT * FROM users WHERE name=?"
cursor.execute(query, (user_input,))
Attack types
→In-band: Error-based or UNION-based data extraction
→Blind: Boolean or time-based (no visible output)
→Out-of-band: DNS/HTTP exfiltration channels
Mitigations
Always use parameterized queries / prepared statements
Use an ORM that handles escaping (SQLAlchemy, Hibernate)
Apply least privilege to database accounts
Web Application Firewall (WAF) as additional layer
Learn more

Cross-Site Scripting (XSS)
CWE-79 · OWASP A03:2021

User input is embedded in HTML output without encoding. Attackers inject scripts that execute in other users' browsers — stealing session cookies, redirecting users, or defacing pages.

// Safe: use textContent

// Or encode server-side

→Reflected: Script in URL parameter, reflected in response
→DOM-based: JavaScript itself writes attacker-controlled data to DOM

Output encoding per context (HTML, JS, CSS, URL)
Content Security Policy (CSP) header
Use textContent instead of innerHTML in JS
HttpOnly and Secure flags on session cookies

Path Traversal
CWE-22

User-controlled input is used to construct file paths without sanitizing "../" sequences. Attackers can escape the intended directory and read or write arbitrary files (e.g., /etc/passwd, private keys).

● vulnerablePython
# Input: ../../etc/passwd
path = "/app/files/" + filename
with open(path) as f: ...

# Safe: resolve and check prefix
base = Path("/app/files").resolve()
full = (base / filename).resolve()
if not str(full).startswith(str(base)):
    raise PermissionError
Mitigations
Resolve canonical path and verify it starts with allowed base
Use allowlist of valid filenames (not blocklist of "../")
Run file server with minimal OS permissions (chroot/container)

Category 03 · Concurrency

Race Condition Vulnerabilities

Race conditions occur when the behavior of a system depends on the relative timing of events — and that timing can be influenced by an attacker. A check made at one point in time may no longer be valid when an operation is performed moments later. These bugs are notoriously hard to reproduce and test.

Privilege escalation Authentication bypass Double-spend attacks Data corruption High severity
Vulnerability Types
⏱️
TOCTOU (Time-of-Check to Time-of-Use)
CWE-367

A security check (access(), exists()) is performed at one moment, but the resource is used at a later moment. Between check and use, an attacker can swap the resource (via symlink) to bypass the check.

● vulnerableC (Unix)
// CHECK: is this a safe file?
if (access(path, W_OK) == 0) {
    // ... attacker replaces with symlink ...
    // USE: now writes to /etc/passwd!
    fd = open(path, O_WRONLY);
}
// Safe: open() then fstat() the fd
// Don't use path-based checks
Classic attack pattern
1.Attacker creates a file they own: /tmp/safe.txt
2.Victim process checks /tmp/safe.txt → OK
3.Attacker replaces with symlink → /etc/shadow
4.Victim process opens /tmp/safe.txt → writes to /etc/shadow
Mitigations
Use open() to obtain file descriptor, then fstat() on the fd (not path)
Use O_NOFOLLOW flag to prevent symlink following
Avoid predictable temp file paths; use mkstemp()
Operate in private directories inaccessible to attackers
Learn more
🎯MITRE CWE-367 — TOCTOU Race Condition↗ 📘OWASP — TOCTOU Explained↗

Web Race Conditions
CWE-362

Modern web apps perform check-then-act logic (check balance → deduct). Sending concurrent requests can execute the action multiple times before the state is updated — enabling double-spending, limit bypasses, or repeated use of single-use tokens.

● race windowPython (Flask)
# Two requests hit simultaneously
balance = db.get(user_id)   # both read $100
if balance >= amount:       # both pass check
    db.set(user_id,           # both deduct!
          balance - amount)  # balance = $0, not -$100

# Safe: atomic DB transaction
db.execute("UPDATE ... WHERE balance >= ?")
Mitigations
Use database transactions with proper isolation levels
Use atomic compare-and-swap (CAS) operations
Apply pessimistic locking (SELECT FOR UPDATE)
Rate-limit sensitive endpoints; deduplicate requests with idempotency keys
Learn more

Signal Handler Race Condition
CWE-364

Unix signal handlers interrupt execution at unpredictable points. If a signal handler calls non-reentrant functions (malloc, free, printf) that were already executing, it can corrupt global state or cause use-after-free scenarios.

Mitigations
Only call async-signal-safe functions from signal handlers
Use volatile sig_atomic_t flags; handle logic in main loop
Block signals during critical sections with sigprocmask()
Learn more

Symlink Race (Insecure Temp Files)
CWE-377

Using predictable temp file names in world-writable directories (/tmp). An attacker creates a symlink with the predicted name pointing to a sensitive file before the victim process creates it.

● vulnerableC
// Predictable name — attacker pre-creates
// /tmp/myapp.tmp -> /etc/passwd
char *tmp = "/tmp/myapp.tmp";
fd = open(tmp, O_WRONLY|O_CREAT);

// Safe: unpredictable, exclusive create
char tmp[] = "/tmp/myapp.XXXXXX";
fd = mkstemp(tmp);
Mitigations
Always use mkstemp() / mkdtemp() for temp files
Use O_CREAT | O_EXCL flags for atomic exclusive creation
Operate in application-owned directories, not /tmp
Learn more

Category 04 · Information Leakage

Side-Channel Vulnerabilities

Side-channel attacks extract secret information not from the algorithm's output, but from physical or observable side effects of its execution — timing, power consumption, electromagnetic emissions, or cache behavior. These attacks bypass cryptographic correctness entirely and are often invisible to standard security testing.

Cryptographic key recovery Password extraction Cross-VM data leakage Cross-origin data theft High severity
Vulnerability Types
⏱️
Timing Attack
CWE-208

Code that short-circuits comparison (returns early on first mismatch) leaks information about the secret through response time differences. By measuring response time, attackers can brute-force secrets byte-by-byte.

● vulnerable (early exit)Python
# Returns faster when more chars match!
def check_token(provided, expected):
    if provided == expected:  # timing leak
        return True

# Safe: constant-time comparison
import hmac
return hmac.compare_digest(provided, expected)
Attack method
1.Attacker sends hundreds of requests with varying first byte
2.Measures which first byte causes slightly longer response
3.Correct first byte found → moves to second byte
4.Repeats — recovers entire secret in O(n×256) requests
Mitigations
Use constant-time comparison functions (hmac.compare_digest)
Use HMAC-based token verification instead of direct comparison
Add random jitter to responses (less reliable — use constant-time instead)
Learn more
📝Coda Hale — A Lesson in Timing Attacks↗ 🎯MITRE CWE-208 — Observable Timing Discrepancy↗
💻
Cache-Timing (Spectre / Meltdown)
CVE-2017-5753 / CVE-2017-5754

CPU performance optimizations (speculative execution, out-of-order execution) leave traces in the CPU cache. By measuring cache access times, attackers can infer the values of speculatively accessed memory — including kernel memory from userspace.

Spectre in brief
1.Train branch predictor to speculatively execute attacker's code path
2.Speculative execution accesses secret memory (e.g., kernel data)
3.CPU reverts the logical result, but cache state persists
4.Attacker measures cache timing to recover the secret bits
Mitigations
Apply OS and firmware microcode patches (Retpoline, IBRS, STIBP)
Site isolation in browsers (prevents cross-origin exploitation)
Reduce timer resolution in browser APIs (SharedArrayBuffer restrictions)
Process isolation for sensitive workloads
Learn more

Power Analysis
CWE-1300

The power consumed by a microprocessor during cryptographic operations correlates with the data being processed. Simple Power Analysis (SPA) and Differential Power Analysis (DPA) can recover cryptographic keys from hardware devices (smart cards, HSMs, IoT).

DPA in brief
1.Attacker captures thousands of power traces during encryption
2.Statistical analysis correlates power with intermediate values
3.Key bits recovered one subkey at a time
Mitigations
Use power-analysis resistant crypto implementations (masking)
Add random noise to power consumption (hardware-level)
Use hardware security modules (HSMs) with built-in countermeasures
Learn more

CWE-203

On shared hardware (cloud VMs, shared caches), an attacker co-located on the same physical host can monitor cache access patterns of a victim's process. Used to extract RSA keys, keystrokes, and AES operations across VM boundaries.

Use cache-oblivious cryptographic implementations

CPUs emit acoustic noise and electromagnetic radiation correlated with their computations. Researchers have demonstrated RSA key extraction by recording the sounds from a laptop's fan/coils, and full key recovery via EM emissions from smart cards at distance.

Mitigations
Physical security: Faraday cages, shielded hardware
Algorithmic: constant-time and power-balanced implementations

🔨
Rowhammer
CWE-1251

Rapidly reading the same DRAM memory row causes electrical disturbance in adjacent rows, flipping bits. Attackers can use JavaScript to repeatedly "hammer" memory rows, flipping bits in page tables to escalate privileges — without any software vulnerability.

Rowhammer in brief
1.Attacker allocates memory adjacent to a target page (e.g., page table)
2.Hammers the adjacent rows millions of times per second
3.A bit flips in the target page (e.g., read-only → writable)
4.Attacker now has write access to arbitrary physical memory
Mitigations
Use ECC (Error-Correcting Code) RAM to detect/correct bit flips
Memory controllers with Target Row Refresh (TRR) support
OS: Guard pages and memory isolation between processes
Browsers: Reduce timer precision to limit hammering rates
Learn more

Impact: Billions of devices affected; significant performance overhead from patches.

Researchers demonstrated ECDSA private key recovery from OpenSSL via a tiny timing side channel in scalar multiplication — exploitable with only a few hundred signatures.

Impact: Required immediate OpenSSL patching; affected all ECDSA-secured communications.

2021Hertzbleed (CVE-2022-24436)Power/Frequency

CPU frequency scaling (Intel/AMD) correlates with data values being processed. Researchers used this to recover cryptographic keys remotely over network timing — a power side channel exploitable without physical access.

Impact: Affected SIKE post-quantum key encapsulation — remotely exploitable.
