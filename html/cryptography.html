Cryptography

Cryptography secures information and communication. It enables confidentiality (encryption), integrity (hashing), authenticity (signatures), non-repudiation, and authentication & authorisation. Real implementations combine multiple primitives — no single algorithm does everything.

🔒Confidentiality — Encrypt data at rest and in transit
✍️Non-repudiation — Prove origin of a message
🪪Authentication — Verify identity of users & services
🛡️Integrity — Detect tampering with data
🔑Key exchange — Establish shared secrets securely
🧩Secret sharing — Distribute secrets across parties
01 · Hashing

Secure Hashing

A cryptographic hash function maps data of any size to a fixed-size digest in a one-way, deterministic fashion. The same input always produces the same output, but it must be computationally infeasible to reverse the hash or find two inputs that produce the same hash (collision resistance). Hashing is the foundation of integrity, password storage, digital signatures, and MACs.

Integrity Password storage Digital signatures Message authentication
Core Properties
🎯
Hash Function Properties
Required security properties

A cryptographic hash function must satisfy three core security properties. Breaking any one of them makes the hash function unsuitable for security purposes.

Properties
Pre-image resistance Given h(x), infeasible to find x 2nd pre-image resist. Given x, infeasible to find x' where h(x)=h(x') Collision resistance Infeasible to find any x,x' where h(x)=h(x') Avalanche effect 1 bit change → ~50% of output bits change

HMAC — Keyed Hash
RFC 2104

A Hash-based Message Authentication Code combines a secret key with the hash. It proves both integrity (data wasn't tampered) and authenticity (sender knows the key). Used in JWT, API authentication, TLS.

HMAC Construction
HMAC(K, m) = H((K ⊕ opad) || H((K ⊕ ipad) || m)) K = secret key (padded to block size) m = message opad = 0x5c repeated ipad = 0x36 repeated // Python import hmac, hashlib mac = hmac.new(key, msg, hashlib.sha256).digest()
Use HMAC when you need
Verifying message integrity AND authenticity together
API request signing (HMAC-SHA256)
JWT signature (HS256 = HMAC-SHA256)
Always use constant-time comparison when verifying

02 · Symmetric

Symmetric Cryptography

The same secret key is used for both encryption and decryption. Extremely fast — orders of magnitude faster than asymmetric crypto. Used for bulk data encryption (files, TLS record layer, disk encryption). The core challenge: how do two parties securely agree on the shared key? That's solved by key exchange (asymmetric crypto).

Confidentiality Bulk data encryption Fast & efficient Requires shared secret
Block Ciphers & Modes of Operation
🧱
AES — Advanced Encryption Standard
FIPS 197 · NIST 2001

The world's most widely deployed symmetric cipher. AES operates on 128-bit blocks using 128, 192, or 256-bit keys. It is a substitution-permutation network with 10–14 rounds depending on key size. Hardware acceleration (AES-NI) makes it extremely fast.

AES Encryption Flow
Plaintext (128-bit block) ↓ AddRoundKey (XOR with key) ↓ [×N rounds]: │ SubBytes (S-box substitution) │ ShiftRows (row rotation) │ MixColumns (linear mixing) │ AddRoundKey ↓ Final round (no MixColumns) Ciphertext (128-bit block)
Key sizes
AES-128 — 10 rounds, fast, sufficient for most uses
AES-256 — 14 rounds, recommended for long-term data & PQC era

ChaCha20-Poly1305
RFC 8439

A modern stream cipher (ChaCha20) combined with an authenticator (Poly1305) — forming an AEAD. Designed by Daniel Bernstein. Preferred over AES-GCM on devices without AES hardware acceleration. Used in TLS 1.3 and WireGuard.

AEAD: Encrypt-then-MAC

Best Practices — Symmetric
Always use an AEAD mode (GCM or ChaCha20-Poly1305)
Never reuse a nonce with the same key — use random 96-bit nonces
Verify the authentication tag before decrypting
Use 256-bit keys for long-term or high-sensitivity data
Rotate keys regularly; support key versioning

03 · Asymmetric

Asymmetric (Public-Key) Cryptography

Uses a mathematically linked key pair: a public key (share freely) and a private key (keep secret). Anything encrypted with the public key can only be decrypted with the private key, and vice versa. Solves the key distribution problem — but is 1000–10,000× slower than symmetric crypto. In practice it is used for key exchange and digital signatures, not bulk encryption.

Key exchange Digital signatures Authentication Non-repudiation
Algorithms & Use Cases
🔢
RSA
RFC 8017 (PKCS#1)

Based on the hardness of factoring large integers. Still widely used for TLS certificates, JWT (RS256), and legacy systems. Requires large key sizes for security.

RSA Key Generation
1. Choose large primes p, q (each 1024+ bits) 2. n = p × q (modulus) 3. φ(n) = (p-1)(q-1) 4. Choose e: gcd(e, φ(n)) = 1 (public exp.) 5. d = e⁻¹ mod φ(n) (private exp.) Public key: (n, e) Private key: (n, d) Encrypt: c = mᵉ mod n Decrypt: m = cᵈ mod n

Elliptic Curve Cryptography (ECC)
NIST SP 800-186

Based on the algebraic structure of elliptic curves over finite fields. Provides equivalent security to RSA with much smaller key sizes — a 256-bit ECC key is as strong as a 3072-bit RSA key. Preferred for modern systems.

Digital Signatures
RSA-PSS, ECDSA, EdDSA

A digital signature proves that a message was created by the holder of a private key and has not been altered. Verifiable by anyone with the corresponding public key — enabling non-repudiation.

Signature Flow
Signing hash = SHA-256(message) sig = Sign(privKey, hash) → send: (message, sig, pubKey) Verification hash' = SHA-256(message) valid = Verify(pubKey, sig, hash') → valid iff hash' == recovered_hash
Signature Algorithm Recommendations
Prefer Ed25519 (EdDSA) for new systems — fast, safe, no random needed
Use ECDSA with P-256 for NIST/FIPS compliance
Use RSA-PSS (not PKCS1v1.5) if you must use RSA
Never sign raw data — always sign H(data)

Diffie-Hellman Key Exchange
DH / ECDH / X25519

Allows two parties to derive a shared secret over an insecure channel without ever transmitting the secret itself. The foundation of forward-secure key exchange in TLS, SSH, and Signal.

ECDH Key Exchange
Alice Bob Generate ephemeral key pair Generate ephemeral key pair (privA, pubA) (privB, pubB) ─── pubA ──────────────────────→ ←─────────────────── pubB ─── shared = ECDH(privA, pubB) shared = ECDH(privB, pubA) (Both arrive at the same shared secret)
Forward Secrecy
Use ephemeral key pairs per session (ECDHE/DHE)
If private key is later compromised, past sessions remain safe
TLS 1.3 mandates ephemeral key exchange — no static RSA

04 · Key Management

Keys, Passwords & Encoding

Cryptography is only as strong as its key management. Generating weak keys, storing them insecurely, or deriving them from passwords incorrectly undermines everything else. This section covers the full lifecycle: generation, derivation from passwords, exchange, storage, and encoding for transmission.

Key generation Password hashing Secret storage Secret sharing Base64 encoding
Key Generation & Sources of Randomness
🎲
Cryptographically Secure Randomness
CSPRNG — never use Math.random()

Keys must be generated from a Cryptographically Secure Pseudo-Random Number Generator (CSPRNG). Regular random functions (Math.random, rand()) are not secure — they are predictable. The OS provides secure entropy from hardware sources.

Secure Key Generation
# Python — OS CSPRNG import secrets key = secrets.token_bytes(32) # 256-bit AES key // Node.js const key = crypto.randomBytes(32); // Go key := make([]byte, 32) io.ReadFull(rand.Reader, key) // CLI openssl rand -hex 32
Rules
Always use OS-provided CSPRNG (urandom, CryptGenRandom)
Never seed with time, PID, or predictable values
Generate keys at full security strength (128+ bits of entropy)

Key Derivation from Passwords (KDF)
PBKDF2 · bcrypt · Argon2id · scrypt

Passwords have low entropy and cannot be used directly as cryptographic keys. A Key Derivation Function (KDF) is deliberately slow and memory-intensive to thwart brute-force and GPU attacks. Always use a unique per-user salt.

Secret Sharing (Shamir's Secret Sharing)
Shamir 1979

A secret can be split into n shares such that any k of n shares can reconstruct it, but k−1 shares reveal nothing. Used in distributed key management, cryptocurrency wallets, and cryptographic ceremonies.

Shamir (3-of-5) Example
Secret S split into 5 shares Any 3 shares can recover S: Share 1 + Share 3 + Share 5 → S ✓ Share 2 + Share 4 → ? (insufficient) Based on polynomial interpolation: f(x) = S + a₁x + a₂x² (mod prime) Shares: (1,f(1)), (2,f(2)) ... (5,f(5))

05 · Protocols

Real-World Cryptographic Protocols & Systems

Individual cryptographic primitives are combined into protocols and systems that solve real-world security problems. Understanding how TLS, PKI, and Blockchain work shows how hashing, symmetric crypto, asymmetric crypto, and signatures are orchestrated together.

TLS / HTTPS Public Key Infrastructure Blockchain SSH
How TLS 1.3 Works

🔒 TLS 1.3 Handshake Flow

1

ClientHello

Client sends: supported cipher suites, TLS version, key_share (ephemeral X25519/P-256 public key), random nonce. No round-trip needed — client speculatively includes key share.

2

ServerHello + Key Derivation

Server responds with its own key_share, selected cipher suite. Both sides now compute the shared secret via ECDHE and derive the handshake traffic keys using HKDF.

3

Server Certificate + Signature

Server sends its X.509 certificate (public key + identity) and a signature over the handshake transcript. Client verifies certificate chain up to a trusted root CA (PKI).

4

Finished Messages (Authenticated)

Both sides exchange Finished messages — an HMAC over the full handshake. This confirms both parties derived the same keys and detects any tampering.

5

Application Data (AES-256-GCM or ChaCha20-Poly1305)

All further data is encrypted with AEAD ciphers using the derived session keys. TLS 1.3 has perfect forward secrecy — past sessions remain safe even if the server's private key is later compromised.

ℹ️
TLS 1.3 improvements over TLS 1.2: Removed RSA key exchange (no forward secrecy), removed weak ciphers (RC4, 3DES, MD5/SHA-1), reduced handshake from 2 round-trips to 1, added 0-RTT resumption. Always disable TLS 1.0 and 1.1.
How PKI Works

🏛️ Public Key Infrastructure (PKI)

1

Certificate Authorities (CAs)

A CA is a trusted third party that signs X.509 certificates. Root CAs are self-signed and their public keys are pre-installed in browsers/OS. Intermediate CAs are signed by roots to limit blast radius of compromise.

2

Certificate Issuance (CSR)

An entity generates a key pair, creates a Certificate Signing Request (CSR) containing their public key and identity (domain name, org). The CA verifies identity (DV/OV/EV) and signs the certificate with its private key.

3

Certificate Validation

Client receives server cert → builds chain to trusted root → verifies each signature → checks validity dates → checks OCSP/CRL for revocation. All checks must pass.

4

Certificate Transparency (CT)

All publicly trusted certificates must be logged to public CT logs (RFC 6962). Allows domain owners to detect mis-issued certificates. Browsers reject certs not in CT logs.

5

Let's Encrypt & ACME

Free, automated certificate issuance via the ACME protocol (RFC 8555). Proves domain control by serving a challenge token. Used by millions of websites — eliminated the cost barrier to HTTPS.

How Blockchain Uses Cryptography

⛓️ Blockchain Cryptographic Primitives

1

Merkle Trees (SHA-256)

All transactions in a block are hashed in pairs, building a binary tree. The Merkle root (tree root hash) is stored in the block header. Changing any transaction changes the Merkle root — instantly detectable.

2

Chain of Hashes (Tamper Evidence)

Each block header contains the hash of the previous block header. Changing any historical block changes its hash, which invalidates all subsequent blocks. Makes history immutable without controlling >50% of hash power.

3

ECDSA Signatures (Wallet Ownership)

Bitcoin uses secp256k1 ECDSA; Ethereum uses the same. Your private key signs transactions; nodes verify with your public key. The wallet address is derived from a hash of the public key — you never expose the public key until you spend.

4

Proof of Work (Hash Puzzle)

Miners repeatedly hash block_header + nonce until the output starts with enough zero bits. Requires enormous computation to find — but trivial to verify. This is the consensus mechanism securing Bitcoin.

06 · Post-Quantum

Post-Quantum Cryptography (PQC)

A sufficiently powerful quantum computer running Shor's algorithm can factor large integers and solve discrete logarithms in polynomial time — breaking RSA, DH, DSA, and all ECC. Grover's algorithm halves the effective security of symmetric ciphers (AES-128 → 64-bit security). NIST completed its PQC standardization in 2024. Migration is urgent: attackers are collecting encrypted traffic now to decrypt later ("harvest now, decrypt later").

Breaks RSA / ECC / DH Weakens AES-128 → use AES-256 NIST standards 2024 Harvest-now-decrypt-later threat
⚠️
Timeline pressure: NIST finalized the first three PQC standards in August 2024 (FIPS 203, 204, 205). The US government mandated PQC migration for federal systems by 2030. Any long-lived data encrypted today should already be transitioning to hybrid or PQC schemes.

ML-KEM (CRYSTALS-Kyber)
FIPS 203 — NIST 2024

A Key Encapsulation Mechanism (KEM) based on the Module Learning With Errors (MLWE) problem — believed to be hard even for quantum computers. Replaces ECDH/RSA for key exchange. Included in TLS 1.3, SSH, and Signal's PQXDH.

ML-KEM Flow
KeyGen: (pk, sk) ← KeyGen() Encaps: (ciphertext, shared_secret) ← Encaps(pk) Decaps: shared_secret ← Decaps(sk, ciphertext) Parameter sets: ML-KEM-512 → 128-bit security (1632 byte pk) ML-KEM-768 → 192-bit security (recommended) ML-KEM-1024 → 256-bit security
Key sizes vs RSA
Public key: ~1.2 KB (vs 256 bytes for P-256)
Ciphertext: ~1.1 KB — larger than ECDH
Fast: encapsulation & decapsulation in microseconds

Hybrid Schemes (Transition Strategy)
Classical + PQC in parallel

Run classical and post-quantum algorithms simultaneously. The security is the maximum of both: an attacker must break both systems. This hedges against both quantum threats and potential weaknesses in new PQC algorithms. Recommended migration strategy.

Hybrid Key Exchange (TLS)
X25519 (classical ECDH) + ML-KEM-768 (PQC) shared₁ = ECDH(privA, pubB) shared₂ = ML-KEM.Decaps(sk, ct) final_key = HKDF(shared₁ || shared₂) Used in: Chrome/Firefox: X25519MLKEM768 Cloudflare: X25519Kyber768 OpenSSH 9.0+: sntrup761x25519
Migration Roadmap
Inventory all cryptographic assets and their exposure
Upgrade symmetric keys to AES-256 and hashes to SHA-384+
Deploy hybrid key exchange in TLS and SSH first
Migrate signing to ML-DSA or SLH-DSA for new certificates

Quantum Key Distribution (QKD)
BB84 · E91 · Physics-based security

Unlike PQC (mathematics-based), QKD uses quantum mechanical properties of photons to distribute keys. Any eavesdropping physically disturbs the quantum state, making it detectable. Provably secure by physics — but requires specialized hardware and point-to-point fiber links.

BB84 Protocol
Alice sends photons with random polarization states Bob measures in random bases They publicly compare which bases (not values) Keep only matching-basis measurements → key bits Eavesdropper Eve disturbs photons → detectable → Abort and restart if error rate too high
Current limitations
Requires dedicated quantum channel (fiber/free-space)
Limited distance (~100–400 km without repeaters)
Expensive hardware; not internet-scalable today
Complements PQC rather than replacing it
